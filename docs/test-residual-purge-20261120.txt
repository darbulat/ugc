Transaction and recovery behavior
---------------------------------
1. Validate the isolated destination before connecting. Pin the schema version
   to production's inventoried 0145_instagram_profiles; refuse schema drift.
2. In the isolated schema, take NOWAIT table locks and the existing history
   writer barrier with pg_try_advisory_xact_lock. Never wait behind production
   activity. SQL statement/lock/idle timeouts and a transaction budget apply.
3. Match all row fingerprints; verify archived/idle states and working accounts.
   Check every incoming FK, including CASCADE and SET NULL; reject outside rows.
   Check UUID/text/JSON references to roots AND deleted child primary UUIDs.
   Reject identities/bindings shared with other accounts.
4. Save a selective, authenticated Fernet-encrypted backup containing original
   row documents, two original update rows, guard states/functions, schema
   signature and destination identity. Verify decryption before any DELETE.
   Key/ciphertext are owner-only files, not symlinks. The backup directory must
   be private. Existing backups are never overwritten. Nothing is logged raw.
5. Temporarily disable only the 18 approved DELETE guards and coverage UPDATE
   guard. Keep FKs/CHECK constraints and all other triggers enabled. Delete in
   FK child-first order, enforce exact affected counts, apply two updates.
6. Restore every guard before COMMIT. Verify coverage, absence of references,
   and hashes of ALL retained table data in this small isolated rehearsal.
   Record a technical audit event without deleted profile content.
7. Any exception, failed check, timeout or lost connection rolls back the whole
   transaction, including trigger DDL and partial deletions.
8. Restore only into the bound original database/schema with matching schema,
   guards, post-delete baseline and retained-data hashes. Refuse tampering,
   wrong keys, another destination, changed working data and repeated restore.
   INSERT original values/identity sequence IDs in parent-first order. Do not
   rewind sequences. Restore only the two approved update fields.

Historical restore needs six explicitly listed INSERT proof triggers suspended
temporarily: intake_receipt_source, accompaniment_lead_source,

accompaniment_attempt_proof, accompaniment_outcome_proof. These validate the

They are re-enabled before COMMIT. FK/CHECK constraints remain active.

Limits before any separately approved production release
-------------------------------------------------------
This is evidence from the real PostgreSQL schema and synthetic facts, not a
load rehearsal of the complete production database. The rehearsal deliberately
locks/hashes its whole isolated application schema for strong unchanged-data
assertions. Do not enable this broad-lock strategy on a live database.

A production execution release needs a separately reviewed narrow locking and
retained-data strategy, a fresh read-only production inventory and schema
check, a verified operational encrypted backup destination and concrete
current-head approval under AGENTS.md. No flag in this version enables it.
The approved operational backup retention proposal is 24 hours after verified
success; ordinary backups keep their standard rotation. This rehearsal release
neither connects to production nor creates/deletes any production backup.

Do not merge, deploy or execute a production cleanup merely because this
rehearsal succeeds. Report results to the owner first, as requested.
