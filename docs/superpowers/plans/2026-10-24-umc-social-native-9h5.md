## Interface decisions

In `application/social_ports.py`, use `P = AuthenticatedMessengerPrincipal` below only as notation; actual signatures use the existing concrete type.

- Frozen `SocialEditorFacts(owner_id: UUID, profile: BloggerProfile | None, accounts: tuple[SocialAccount, ...])` contains detached facts only. Service checks owner/profile/account UUID consistency and duplicate platforms; invalid/mixed facts are `social_unavailable`.
- Frozen `SocialEditorState(accounts: tuple[SocialAccount, ...], next_platform: SocialPlatform | None)` and `SocialEditorSaved(account: SocialAccount, next_platform: SocialPlatform | None)` preserve the existing HTTP fields; no native tuple/session/ORM object is returned.
- `SocialEditorRepository.read_editor(user_id: UUID, *, principal: P, session: object) -> SocialEditorFacts` starts the read-only snapshot and validates native/status before profile/social reads.
- `SocialEditorRepository.prepare_editor_write(user_id: UUID, *, principal: P, session: object) -> SocialEditorFacts` takes the appropriate complete User barrier and returns current owner-bound facts. It does not create/save/remove anything.
- `SocialEditorPort.editor_state(user_id: UUID, *, principal: P, skipped: Collection[SocialPlatform | str] = (), include_vk: bool = False) -> SocialEditorState`.
- `SocialEditorPort.save_editor_account(user_id: UUID, platform: SocialPlatform | str, url: str, *, principal: P, work_format: WorkFormat | None = None) -> SocialEditorSaved`.
- `SocialEditorPort.remove_editor_account(user_id: UUID, account_id: UUID, *, principal: P) -> bool`.

The facade methods require typed principal explicitly and own exactly one transaction through the existing configured TM; no public `session=None` fallback or `with_optional_tx(None)` branch exists in these three methods. The configured production capability must satisfy `editor_repository is account_repo`; a distinct object with compatible-looking methods is unavailable before SQL. Repository methods require an actual caller `AsyncSession`, the active intended root transaction, no nested transaction and the actual configured SQL bind for the User/profile/social statement families. Validate these relationships using Python/session/factory/bind metadata before executing any SQL; a participant marker or an `execute` attribute is insufficient. Unknown, memory/SQL-mixed, wrong-engine, inactive/nested or pending-ORM-change sessions are unavailable, rather than flushed or probed with a SELECT. They never open/commit a second session. Legacy `list_accounts/save_account/remove_account/next_platform(..., session=None)` remain explicit trusted methods, but the router never invokes them as a fallback.

Add `editor_repository: SocialEditorRepository | None = None` after existing service constructor fields so old positional construction remains compatible. Missing capability must be a named unavailable result, not a no-op successful stub. Do not infer that an arbitrary object/fake session is SQL merely because it exposes `execute`.

Every new read fact projection disables incidental ORM autoflush and uses detached selected values or explicitly fresh loading. Build and validate the complete detached `SocialEditorState`/`SocialEditorSaved` result, including its entire account projection and next-platform value, before leaving the facade-owned transaction; projection/result-validation failure rolls back the change. HTTP response-model encoding happens afterward. A later HTTP serialization failure is safely reported with constant no-store 503 but does **not** imply rollback of an already committed mutation. Tests must preserve that distinction; do not add a generic transaction/encoding framework or claim a stronger guarantee.
