## One authoritative consent predicate, including binding epochs

This is a prospective 10b consent contract/alignment, not a retroactive proven 10a review defect. Root approved that an opt-in applies to the exact binding epoch/context the creator reviewed. A → B → A requires a fresh current-context opt-in even when owner, IG and `created_at` return to their old values. Identity/grant/policy eligibility must also be current; an invitation or registration agreement never supplies consent.

Define a **binding epoch** as one uninterrupted canonical direct relation `(referred_user_id, referrer_user_id, created_at)`. The first covered active observation starts an epoch. An inactive observation, absence/delete, subject change or changed relation tuple ends it. A later return starts a new epoch. Repeated identical active observations without an intervening transition belong to the same epoch; they cannot reactivate an old consent or create new consent. The current trigger already suppresses identical tuple UPDATEs, so a harmless repeated admin write does not change epoch. A delete/reinsert, including in one transaction, is a real interruption because immutable inactive/active observations remain present.

Introduce one resolver used by foundation settings, consent allow validation, audience preview/submit/review, and the later worker. Its resolved fact contains `binding_epoch_sequence` (the first active sequence of the current contiguous epoch), current canonical tuple and the exact observed witness. Prospective `consent_context` uses the same v1 purpose, actor/owner/IG/UTC `binding_created_at` keys with `binding_sequence` set to this normalized epoch sequence. Do not change historical receipts.

For a retained 10a consent, load its exact `(actor_id, operation_key)` foundation receipt and recorded `consent_context`. Verify that digest against an actual immutable active observation for that consent's actor/owner/IG/created_at in the current uninterrupted epoch; this supports a historical context issued from a harmless repeated observation in that same epoch. Do not invent an observation, accept matching owner/IG alone, use an arbitrary observation from an earlier A epoch, or use wall-clock comparisons as proof of transaction order. Missing receipt/context, missing coverage, ambiguous or unresolvable proof is unavailable/ineligible. A newly submitted source stores the concrete witness and normalized epoch sequence, so later stages need no opaque-hash search.

Effective consent requires all of: latest creator consent event is active; its authenticated actor is that creator; exact owner/current IG/current epoch match; its publication version, terms version and hash match the current enabled publication; creator and owner are active; owner has a current active publisher grant; creator has a usable private Telegram contact. Settings must use this same predicate and expose a safe reason plus `can_consent` for a stale epoch. Allow commands still require the displayed current context and exact current terms before checking an old receipt; an old successful command cannot silently opt into a new epoch. Unsubscribe always acts on the creator's own latest consent stream and remains available while eligibility, grant, publication or accounts are paused.

## Draft and filter contract

New pure types live in `domain/campaign_review.py`, not the foundation's `Action` union. `CampaignDraftContent` is title, plain text and an optional product/reference HTTPS link. `CampaignSegmentV1` allows only these optional fields: `country`, `region`, `city`, `topics_any`, `profile_work_format`, and `social` with exactly `platform`, optional `work_format`, `followers_min` and `followers_max`. All populated top-level dimensions AND together; `topics_any` matches any selected topic. There is one social predicate, whose presence requires an attached account on that platform. Omitted filters mean the eligible own network; explicit null/empty arrays/unknown fields, bool-as-int thresholds, negatives and min > max are rejected. A numeric zero is an actual follower threshold, never an unlimited quota.

`platform` is exactly the existing `SocialPlatform` enum (`instagram`, `tiktok`, `youtube`, `telegram`, `vk`); formats use `WorkFormat` (`ugc_only`, `ads_in_account`). Geography compares existing profile fields using `application/geography.py::normalize_geo_token` with exact normalized equality. Country selection maps enabled `CountryRepository` values to their existing profile representation; it never equates ISO code and stored name by guess. Region/city are stored free text: the existing city helper deliberately has no country/region taxonomy. Topic values are the existing normalized strings in `profile.topics["selected"]`, not invented topic IDs; the current registration validator only limits their count. The filter-fields allowlist is a versioned application contract, not a nonexistent published-policy option. Metadata may supply current country choices and observed safe values from consenting own candidates, with no contacts; it does not disclose nonconsenting members individually. No geocoder/network request runs during evaluation.

Numeric filtering requires independent proof of a **successful metric observation**, not a recent collection attempt or current identity alone. The existing `InstagramStatsCollectorService._mark_failed_attempt` calls `touch_fetched_at`, which changes only `InstagramStatsModel.fetched_at` and leaves the old count/provider/identity intact. Therefore no `InstagramStatsModel` row is admitted numerically on those fields alone, even when its identity matches and its timestamp is recent. Likewise, `creator_social_v1` and manual-code verification create `metrics_source="legacy_profile"` projections; a current `external_id`, `verified=true`, `verification_observed_at` or copied `metrics_fetched_at` does not turn that copied count into an independent metric observation. The existing `instagram_graph_api` source string is also not, by itself, a reference to retained successful-measurement proof. Do not stamp historical data with a new success time or infer it from raw-response presence, profile `updated_at`, migration time, identity-verification time, provider name, or latest attempted fetch.

Until a separately reviewed trusted successful-observation writer supplies the following contract, these legacy stats/social paths are **metric unknown** and fail numeric filters in preview, submission and review. 10b does not create a collector or silently grant trust to an existing source string. Attachment/work-format filters still work, and nonnumeric segments remain usable; UI states the missing measurement provenance instead of promising numeric coverage. This rule applies to other networks as well: a persisted self-reported count/source/time may be displayed with its actual provenance, but is not numerically eligible without a specifically admitted measurement proof. Never substitute zero or estimate reach/audience demographics.

Future admitted `MetricObservation` proof must be immutable and server-owned, with a unique observation/business key; creator UUID, platform, concrete social-account identity and the current canonical IG identity at measurement; nonnegative count; an explicit allowlisted trusted writer/provider; successful outcome; `successful_observed_at` and committed `recorded_at`; and a retained real response/evidence reference or digest sufficient to verify the exact account/count. The only prospective source classes are an actual successful authenticated platform API response or an explicitly reviewed configured provider's successful response; imports, request-body assertions, `legacy_profile`, manual-code/cutover projections and identity proof alone are not admitted. A source label such as `instagram_graph_api` is not automatically migrated into either class. A trusted writer appends this proof only after validating a real successful measurement for that identity, never when touching backoff/attempt time or copying old values. `successful_observed_at` is the trusted successful response observation time, distinct from collection-attempt timestamps; any separately retained provider measurement time is named and validated independently. Existing failures cannot advance it.

Numeric eligibility uses `0 <= as_of - successful_observed_at <= policy.limits.metrics_max_age_seconds`, exact current account/IG matches and a supported proof version. Select the newest eligible **successful** observation by that time and then immutable observation ID; recent attempt timestamps never participate. Unknown, future, stale and mismatched proofs get separate safe exclusion reasons. Freeze observation ID, exact count, source/evidence digest, successful time, account/identity and proof version in submission/approval evidence. Without a numeric filter, unknown metrics do not exclude an otherwise valid attachment. Historical rows lacking proof remain unknown until a genuinely new successful observation; no historical stamping/backfill is authorized.

Content preserves the exact reviewed code points after trimming outer input whitespace once at draft save; there is no later translation, interpolation of caller HTML or URL rewriting. Validate title, campaign text and optional product/reference link against actual published `title_max_chars`, `text_max_chars` and `link_max_chars`. Invalid HTTPS schemes, credentials, controls/whitespace, malformed ports and local/loopback/link-local destinations are rejected; no server fetch/preview is performed. Missing policy gives a named setup state, not a fallback size or quota. Policy values may be synthetically small in tests; a value of 7 in foundation fixtures is not a product promise.

Submission seals an immutable `CampaignEnvelopeV1` for **all five** supported locales (`ru`, `en`, `kk`, `be`, `uz`): the exact displayed sender-label snapshot and its source fingerprint; content-addressed template version; default-locale choice; trusted Mini App base snapshot; and each fully rendered `ReceiptMessage` payload (`channel="telegram"`, exact plain `text`, exact `action_url`, exact `action_label`, `parse_mode=None`). A nonzero campaign UUID is reserved at draft creation, so the actual URL `...?campaign=<that UUID>` is already known and rendered now. No placeholder URL/UUID, approximate sender-length allowance or late base-URL substitution can pass the length check. Store a digest of each complete locale payload and a digest of their ordered map plus sender/template/default-locale metadata. The sealed sender and five locale previews are the message the moderator sees; any current owner-profile label shown separately must be clearly identified as current account metadata, not the message sender.

Validate the complete exact plain-text body, including sender prefix, line breaks, title, campaign text, product/reference link and localized envelope copy, at **1–4096 characters**. That technical Telegram bound is stated in the installed `aiogram/methods/send_message.py`; it is independent of published business content limits. Use a conservative additional ceiling of 4096 UTF-16 code units so astral emoji cannot bypass the provider bound; test both exact-boundary and one-unit-over cases with long labels and all five locales. The native action URL/label are distinct stored keyboard fields, not guessed text-link bytes: validate their exact rendered values with the receipt adapter's HTTPS/private-action contract and include them in the payload digest. If the template renders any URL in `text`, that actual string also counts in the body bound. Every locale must pass before submission/approval; never truncate, omit a locale or retranslate campaign content to make it fit. Worker preparation later revalidates the stored payload/digest/technical limit and selects a stored locale payload; it cannot rebuild it from current labels, templates or configuration.

Every save creates an immutable `(campaign_id, revision_number, content_digest, segment_digest, revision_digest)`; a small versioned projection points to the current revision. `revision_digest` covers owner, normalized content, typed segment/schema version and policy publication/hash used to validate it. Draft save/replace needs an authenticated active owner and current active grant/current enabled policy. A replaced publication requires a new saved revision validated against its actual limits before submission. Reads and safe owner cancellation remain available after grant loss. Editing submitted/approved content in place is forbidden. A rejected/expired unstarted task may produce a new revision and new submission; any previous submission/review/source stays readable. Once an attempt ever exists, create a new campaign for different content.

## Preview, submission and audience freeze

Preview is a signed POST under a read-only repeatable snapshot. It returns campaign/revision and policy/grant versions, `as_of`, aggregate own-network/segment/eligible counts, disjoint first-exclusion counts in a documented order, current measured/reserved capacity and an opaque fingerprint. It does not reserve quota, append commands, reveal destination/phone/nonconsenter IDs, or guarantee that submission will accept the same audience. Unavailable history/schema/source is an explicit unavailable result/503; a real zero is an honest empty result. A changed preview never automatically resubmits.

Source evaluation starts from the authenticated owner's direct registered network. A candidate must be nonself, current active registered confirmed creator, have current nonblank canonical IG and a usable positive ASCII private Telegram ID, match the typed segment and have effective epoch-scoped consent. Pending referrals, unconfirmed creators, MAX-only contacts, paused/blocked/bot-blocked/deleted users and foreign networks cannot enter it. Contact social URLs and request body addresses are never delivery sources. Normalize numeric Telegram IDs before comparing (leading-zero spellings are the same destination).

Deduplicate recipient UUIDs, canonical IG and normalized Telegram destination. If the canonical unique-IG invariant is violated, expose an integrity-unavailable condition and create no source. If several eligible accounts share one destination, exclude every ambiguous member of that destination group; do not pick an arbitrary winner. Keep duplicate-destination counts aggregate. Per-recipient capacity later also protects durable creator UUID/current IG/destination keys so aliases and cross-owner use cannot bypass frequency limits.

Submission requires `campaign_id`, expected campaign version, exact current `revision_digest`, and the preview's exact policy publication/hash. The server recomputes candidates and eligibility under the write protocol. It may seal the actual current result if preview drifted, but the returned submitted count/digest is explicit; the owner's submit screen says preview is an observation, and the owner may cancel pending review. Zero eligible or a count above actual `recipients_per_campaign` fails without an event, usage increment or silent truncation.

An immutable submission has `submission_id`, campaign revision/digests, publication/terms hash, current grant version, server `submitted_at`, review deadline, segment schema/digest, complete candidate-set digest and the exact immutable `CampaignEnvelopeV1` snapshot/map/digests. Its submission digest covers both source membership and the complete envelope metadata/payload map. At submission, lock/refresh an existing `AdvertiserProfileModel` sender-brand row before snapshotting it; the current label resolver prefers that mutable brand, and neither User nor history barriers protect its ordinary merge writer. If no brand row exists, capture the canonical fallback under the history barrier, or the exact localized unnamed-sender strings in the envelope. A concurrent later insertion cannot replace a sealed fallback. Freeze the exact label source chosen at that statement; review/approval never resolve it again. Store one source per eligible recipient: immutable source ID; creator UUID/current IG; normalized binding epoch and exact observation witness; exact active consent event `(creator_id,version)` and command-context proof; relevant profile/social/metric value and independent successful-observation proof fingerprint where required; internal current-contact reference/fingerprint; eligibility timestamp. Private destination stays server-only. A source may never be reassigned to another user/identity/epoch/contact. New invitees and newly opted-in creators never enter this submitted set.

Persist submission, sources, `submitted` event, accepted-submission quota usage and active-campaign occupation, plus the actor operation receipt in one transaction. `review_deadline = submitted_at + published.review_ttl_seconds`; equality is expired. Every accepted new submission consumes `submissions_per_owner` even if rejected/cancelled later. Duplicate replay does not consume again. A new revision/re-submission is a new submission, subject to the same current limits.

## Moderator review and approve/reject contract

Only a different current active UMC admin may review (`reviewer_id != campaign.owner_id`). A publisher who also has `admin=true` cannot approve/reject their own campaign. Queue/detail reads recheck current active admin authority; an old role/capability payload is not authority. Detail shows exact sealed content/link, publication/terms, immutable message sender-label snapshot, template version and complete previews/digests of all five sealed locale envelopes, segment, submitted total, current surviving total and reason breakdown, screening matches and quota impact. Keyword screening annotates the review; it never approves it. No private contacts or address list is returned.

Review detail computes the **entire surviving submitted subset** under current eligibility: same UUID/IG/epoch/contact and exact active source consent event, same current enabled publication and original publisher-grant version still current/active, current segment matches/fresh metrics, no duplicate identity/destination or quota/cooldown conflict. Changed metric/profile facts may keep a source eligible; its approval evidence must record both submitted and current observation. A new consent event cannot revive an excluded sealed source; resubmit to bind that new intent. A revoked/regranted publisher grant or replaced publication requires a new submission, not silent reuse of old moderation.

Detail returns `review_context` covering submission ID, campaign version, immutable revision/submission digests, exact displayed sender-label snapshot/source fingerprint, template version, default-locale choice, full five-locale payload map digest **and each locale envelope digest**, current policy/grant stream versions, reviewer UUID, exact ordered surviving source IDs plus their current eligibility evidence, capacity observation and computed approved-audience digest. Hash stable fact versions/values, quota-window identity and measured/reserved counts; exclude volatile `as_of`/evaluation timestamps, so ordinary time passing does not make every approval conflict. Time-dependent expiry/freshness/cooldown predicates are recomputed at approval and can still invalidate it. The client submits that hash; it never submits candidate IDs, an editable subset, addresses or counts. The server stores/validates the actual source set. An admin cannot widen a submission, approve another sender/template/message under an old hash, or approve a newly generated audience merely because it has the same count.

Approve/reject both carry actor operation key, expected campaign version, submission ID, exact revision digest, `review_context` and nonblank reason. Under locks, refresh all current authority/eligibility evidence and recompute the exact hash/subset using the immutable submitted envelope, not mutable profile/template configuration. Any changed bound value returns 409 and no reservation, review decision or job: refresh the actual detail and review it again. Brand/template deployment changes after submission leave the sealed reviewed payload unchanged; they cannot substitute new text. To use a new brand/template/base URL, save a new revision and submission requiring a new review. There is no silent further shrink at approval. The moderator approves the exact surviving subset and envelope they saw; the subset may already be smaller than the original submission. An empty subset cannot be approved. Insufficient capacity rejects the whole command with a safe reason/counters; it never chooses the first N or silently turns quota shortage into a partial approval.

Approval appends an immutable review row binding reviewer, reason/time, exact publication, submission/revision digests, approved-audience digest and **the same reviewed sender snapshot/source fingerprint, template version, default locale, full five-locale payload map and its per-locale/aggregate digests**; approved-member rows referencing only submitted source IDs; quota reservations; one dedicated delivery job per approved member; campaign version/event and actor receipt, atomically. Exact envelope equality with the immutable submission is a persistence invariant, not a fresh render during approval. Unique `(submission_id,decision)` and `(review_id,source_id)`/job constraints plus expected version prevent concurrent double approval or approve-versus-reject. Rejection appends its own decision/reason and frees active occupation, retaining submission usage/history. Jobs have no attempt/provider reference and remain waiting for delivery implementation. A reviewed rejection is never a delivery failure.

Owner cancellation, review expiry and later dispatch expiry append terminal events, release only unstarted reservations and active occupation, and keep all facts. Cancellation can use authenticated ownership even after grant/policy/account pause, because it prevents new sends. It cannot alter an existing attempt or outcome. Submission expiry and approval can race only through the common lock/version protocol. `dispatch_deadline = approved_at + publication.dispatch_ttl_seconds`; the later worker cannot start at equality or beyond. No mutable expiry may extend the sealed review/dispatch deadline.

## Capacity semantics without invented numeric defaults

Use all actual required `LIMIT_NAMES` from the current publication. Submissions, owner/global/recipient attempted-delivery usage share its configured positive `window_seconds`; all timestamps are UTC. The accounting window for an event at `t` is `[epoch + floor(t/window_seconds)*window_seconds, next boundary)`. `active_per_owner` is the concurrent number of submitted/approved/dispatching campaigns, not drafts or a lifetime historical count. This interpretation makes cancellation/rejection free concurrent capacity, while recorded submission/attempt usage remains consumed.

At approval, reserve one future start per approved member against owner/global/per-recipient configured capacity for the current window and reserve its cross-owner recipient/destination cooldown claim. Count committed starts in the current window **across every policy publication** plus live reservations; never key usage only by policy ID. Per-recipient protection counts creator UUID, current canonical IG and normalized destination scopes, so changing an alias cannot reset limits. Existing historical keys/attempts remain recorded after current identity/contact changes. A different publication's window duration recomputes its current UTC interval from the immutable event times; it cannot clear usage by creating a new counter row. Outstanding unstarted reservations from any publication count until atomically released/revalidated.

Reservation expires at the earlier of dispatch deadline and accounting-window end. At that boundary a later worker must atomically release/re-evaluate and reacquire capacity under the then-current window/limits before preparation; merely carrying the old reservation into a new window is forbidden. Approval never reserves an unbounded future window. Mutating capacity commands settle due unstarted reservation/deadline expiries under the same lock, with immutable release/terminal events before evaluating capacity; read endpoints never do this. Bound expiry work by the actual published batch size and require another explicit command/worker pass if more remain, rather than ignoring stale reservations or doing an unbounded sweep. Cooldown is checked against both actual last starts and other live reservations for any protected recipient/destination scope. Keep the recipient claim until that reserved job is consumed or released; two campaigns cannot concurrently promise starts within `recipient_cooldown_seconds`.

Before a later attempt, current limits still govern. Recompute usage against current policy/window, exact consent/source/grant/reviewer authority and current expiry; if suspended/obsolete, skip or defer with a real reason. A stricter policy never allows over-cap starts because an old reservation exists. Consuming a reservation appends a unique immutable `attempt_started` usage event in the same committed transaction as the exact attempt, even if the later provider returns definite failure or unknown. No result outcome refunds that usage or cooldown; crash after prepare remains charged. Only an unstarted skipped/cancelled/expired reservation is released. A manually reviewed retry of a definite failure would need a new attempt and new capacity/cooldown, while unknown attempts have no resend command. 10b exposes no retry endpoint.

Global/owner starts and `claim_batch_size`, `worker_concurrency`, `starts_per_second` remain published worker contracts. 10b cannot substitute unlimited processing or construct a transport while these are absent. Reserve/consume/release use immutable events and a projection whose totals can be rebuilt. No wallet, financial item, paid entitlement or subscription counter participates.

## Transaction/refresh protocol

Write services take the caller's transaction, use READ COMMITTED and return only detached DTOs. A command either commits all its facts or none. Reuse the existing global campaign advisory transaction lock for this slice; its serialization is intentional and avoids a second inconsistent lock hierarchy. Do not split into new per-owner advisory locks without reviewing the entire foundation/worker order.

1. Read the immutable campaign/submission/review identifiers and preliminary candidate IDs without locking. Gather owner, actor, frozen recipient users and the original reviewer for later preparation. For a new submission, preliminary selection is server-owned and bounded by `recipients_per_campaign + 1`; an over-cap result stops before a large lock set. Missing/inconsistent source is unavailable.
2. Acquire all relevant existing User rows `FOR SHARE` in UUID order. This serializes admin/status/contact changes. Do not acquire a campaign/history lock first and later add a User lock. If refreshed membership requires an additional User, abort with refresh conflict and restart from a new transaction, never acquire it out of order.
3. Acquire shared identity-history advisory lock, then the same campaign exclusive advisory lock as 10a. Re-read authority, binding/identity/history coverage, grant, policy, consent and campaign version/receipt after acquiring them. Binding/profile writers already take the history writer barrier before mutation. A changed preliminary eligible set requires refresh; no partial work is saved.
4. For submission, lock the existing owner `advertiser_profiles` row `FOR SHARE` before selecting its brand; re-read after any wait and freeze the resulting exact sender/envelope into the immutable submission. Advertiser profile merge writes take neither User nor history barriers, so those barriers are insufficient. If that row is absent, the observed canonical fallback remains the sealed value even if a brand is inserted later; no mutable later read may replace it. Then lock exact source social/account rows used by filters and any separately admitted successful-measurement proof projection in stable table/key order, followed by campaign/job projections and quota projections in scope/window/key order. Legacy stats timestamps are never metric proof. Explicit social row shares protect used attachments/count evidence; immutable successful-observation rows need no mutable freshness stamp. Missing/new matching evidence after preliminary evaluation causes refresh or truthful exclusion, never an unlocked substituted source. Approval reads the already immutable sender/template/five-locale payload map and does not call the mutable label resolver or current template renderer. Acquire no new User locks at this point.
5. Obtain the command's authoritative UTC observation time **after** waits; refresh all locked evidence, validate current versions/exact context, validate expected capacity, and append receipt/events/projections atomically. Do not use a stale pre-lock clock to admit an expired review, fresh metric or old quota window. Test the first instant on the other side of each boundary.

Foundation consent/grant/policy commands serialize on the same campaign lock; User authority changes conflict with held User share barriers; canonical identity/binding changes conflict with history barrier; relevant mutable social/measurement projections conflict with row shares. An existing advertiser-brand writer conflicts only with the explicit advertiser row share taken while sealing submission. It may otherwise complete concurrently with review/approval, because those stages use the exact immutable submitted envelope rather than current brand text. Source UUIDs and immutable history references never become cascaded aliases during an account merge. If the canonical user/identity relation changes, future preparation excludes it; no old job is redirected.

Read services set `REPEATABLE READ, READ ONLY` before the first query, return `as_of`, and do no reconciliation/expiry writes during reads. Pure preview metadata cannot be mistaken for a reservation. Same-key/different-intent conflicts bind action, expected version, campaign/submission/revision/context and reason. Same-key/same-intent replay returns the retained original result plus current status/capabilities without rerunning effects; it still checks current actor scope/authority. A previous approval cannot be replayed by a now-nonadmin. Safe ownership reads and cancellation are intentionally separate from new publisher authority.
