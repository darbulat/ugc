# Task9e / O01 — Telegram Mini App checkout design

Status: research/design for root review, 2026-10-23. Only this brief changed during the shared full-gate freeze. Root subsequently reported the shared gate green (5280 passed,1 skipped,98.27%) and released the freeze;9e still requires design review before implementation. No production, migration or test changes, credentials, provider calls or live sends. This extends Task8/9d's actual persisted v1 order and quote; it does not activate financial flags or settle the pending legal/provider/refund-anchor questions.

## Decision

Use one v1 checkout coordinator shared by the signed Telegram Mini App and existing Telegram bot payment entry points. It prepares the existing capture intent, creates a real Telegram invoice link outside every database transaction, persists the returned link, and exposes only server-confirmed payment facts. A single durable pre-checkout authorization per order/intent prevents two payable links from charging the order twice before the first successful-payment update arrives. Authenticated paid receipts must be durably stored before webhook ACK.

Do not route v1 back through an independent `send_invoice` branch: that would bypass the same issuance/authorization fence. Preserve the working legacy bot path for `financial_version is None`. A ready v1 link may be opened through a legitimate Telegram link fallback when the native Mini App invoice method is unavailable; this reuses the same stored invoice rather than issuing another one.

MAX gets actual own-order status and an explicit Telegram handoff for an existing canonical account that really has a Telegram binding. General advertiser-only MAX↔Telegram linking is the necessary next Task9f, described below; numeric ID equality is never identity proof. This limitation does not block the fully tested Telegram path, but O01 across both messengers is not complete without9f.

## Primary documentation checked

- Telegram `createInvoiceLink` returns a link. Its title is1–32 characters, description1–255 characters, payload1–128 bytes; `LabeledPrice.amount` is an integer in the currency's minor units. Use the server's RUB provider configuration and actual frozen components. [Bot API method](https://core.telegram.org/bots/api#createinvoicelink), [price type](https://core.telegram.org/bots/api#labeledprice).
- `WebApp.openInvoice` and `invoiceClosed` are available from Telegram Mini App API6.1. Callback states include paid/cancelled/failed/pending. Treat every callback as a reason to refresh authenticated server facts, never as payment authority. [Mini App method](https://core.telegram.org/bots/webapps#initializing-mini-apps), [events](https://core.telegram.org/bots/webapps#events-available-for-mini-apps).
- Pre-checkout must be answered within10 seconds. Telegram explicitly warns merchants to control multiple payments; paid service messages are the later confirmation. [Payment flow](https://core.telegram.org/bots/payments#7-pre-checkout).
- Non-2xx webhook responses cause Telegram retries, subject to its bounded delivery policy; an HTTP200 before durable receipt persistence loses that protection. [Webhook contract](https://core.telegram.org/bots/api#setwebhook).
- Invoice links have `t.me/$<slug>` or `t.me/invoice/<slug>` forms. [Invoice deep links](https://core.telegram.org/api/links#invoice-links).
- MAX documents an external `WebApp.openLink` requiring a user gesture. The checked bridge reference has no `openInvoice` method; do not transplant the Telegram API onto MAX. [MAX Bridge](https://dev.max.ru/docs/webapps/bridge).

Installed aiogram3.25.0 exposes `Bot.create_invoice_link(..., prices:list[LabeledPrice], provider_data, need_email, send_email_to_provider, request_timeout)->str`; the local signature was inspected without I/O. No SDK upgrade is needed for this method.

## Existing code and concrete gaps

- `application/services/payment_service.py`: `validate_order_for_invoice` checks actual order ownership/NEW status, then `calculate_invoice_data`. For v1, calculation calls `capture_repository.issue` in its own transaction, freezing the actual quote and PENDING payment. Provider-token absence is checked only afterward. New checkout must preflight provider/account/gates before preparing an intent and use a caller transaction for preparation, not call this method twice around I/O.
- `infrastructure/db/repositories/financial_capture.py`: `issue` uses the actual paid items and immutable `financial.capture_intent`; it does not use legacy tariffs. `capture` checks original intent, exact owner/provider account, both charge IDs, currency, amount, quote key/components and trusted protocol time, then writes allocations and the snapshot request. Its exact receipt replay and existing User→order→payment→history→item boundary remain authoritative.
- `container/service_factory.py`: capture is configured only when `bot.telegram_payment_account_id` exists, using `FinancialPolicyService(config.financial)` and trusted identity history. Preserve this provider/account fence; neither account nor provider token comes from the browser.
- `bot/telegram/handlers/payments.py`: bot `/start pay_<uuid>`, `/pay_order` and Pay callbacks currently send invoices. `pre_checkout_query_handler` currently approves every query. Its DTO/Telegram adapter retain payer/payload but omit the query's amount/currency. Add a narrow v1 authorization branch and those actual native fields; do not rely on post-charge rejection.
- That handler's `successful_payment_handler` currently exits for BLOCKED/PAUSE users via `get_user_and_ensure_allowed`. An already-paid v1 receipt must be recorded even if sales/account status later changed; authorization for new sales is separate from recording a real trusted receipt. Unknown or changed payer/owner becomes durable unresolved intake, never a reassigned capture or a discarded payment.
- `telegram_webhook_app.py` validates the webhook secret, but schedules `feed_update` with `create_task` and ACKs200 first. The v1 paid-receipt branch must commit a durable inbox before ACK; post-capture notices may fail/retry independently.
- `miniapp/principal.py` provides strict extra-forbidden envelopes, HMAC resolution and24h freshness/60s clock skew. Preserve those rules. Checkout additionally retains the authenticated platform/external identity until the current User is rechecked under its lock, rather than accepting a body-selected user or trusting a stale resolved UUID across rebinding.
- `miniapp/umc-selection.js` already has a real persisted quote/result, explicit uncertain creation retry and own selection status. Add checkout to that receipt/order view without rewriting the legacy form or inventing payment success.

## Ports and signed API

Proposed new owned modules: `domain/checkout.py`, `application/checkout_ports.py`, `application/services/checkout_service.py`, SQL checkout/inbox repository and models, `infrastructure/messenger/telegram/invoice_links.py`, `miniapp/checkout_api.py`, a durable paid-receipt worker and narrow existing-handler/factory/template integration. Root confirmed `financial_payout_v1` (itself after `campaign_foundation_v1`) as the stable parent of `checkout_v1`. The additive checkout revision is now frozen; root's `campaign_digest_v1` follows it. UI agent owns the concurrent central API/factory/model/HTML foundation edits; coordinate exact central patches with root/UI rather than overwriting those blocks.

Application contracts:

- `CheckoutActor(user_id, platform, external_id)` is constructed only from verified recent signed data/native Telegram updates. No submitted role, Telegram ID, owner, amount, policy, provider/account, URL, paid time or outcome is accepted as proof.
- `CheckoutService.request_invoice(order_id, actor, operation_key)` returns a typed snapshot/attempt state; the initial command is Telegram-only.
- `CheckoutService.retry_link(order_id, actor, operation_key, previous_attempt_id)` is a separate explicit user command for a failed/unknown nonmonetary link-creation attempt, with fresh current gates. It cannot release or replace a payment authorization.
- `CheckoutService.status(order_id, actor)` is a pure own-order read, including during core/new-sales pause. `TelegramInvoiceLinkGateway.create_link(PreparedInvoice)` performs exactly one bounded Bot API call, without DB objects or a generic transport retry wrapper.
- `PreCheckoutAuthorizationService.authorize(native_query)` consumes authenticated Telegram payer/payload/amount/currency/query ID; the endpoint cannot invoke it. `PaidReceiptInbox.accept(authenticated_receipt)` and its processor are likewise private server ingress.

Routes under `/miniapp/api/financial/orders`:

- `POST /{order_id}/invoice`: strict signed envelope plus operation key only.
- `POST /{order_id}/invoice/retry`: strict signed envelope plus operation key and previous attempt ID only; direct user action, no automatic retry from reload/polling.
- `POST /{order_id}/checkout-status`: strict signed envelope only; reject query authority and all additional fields.

Suggested public fields: `order_id`, actual `policy_version`, `currency`, `amount_minor`, `invoice_state` (`not_requested|creating|ready|failed|unknown|untracked`), opaque `attempt_id`, validated `invoice_url` only for an authorized ready result, `capture_state` (`not_recorded|confirmed|unavailable`), actual immutable `captured_at` when confirmed, `writes_paused`, `can_open` and a safe reason code. `not_recorded` explicitly does not assert that a bank has not charged. Do not expose charge IDs, provider token/data/account, raw receipts or another account's status.

## Durable state and transaction boundaries

Keep append-only immutable request/attempt/proof rows plus a small locked current projection. Unique identities cover `(client, operation_key)`, `(provider, configured account, capture_intent_id)`, one active link attempt per checkout, one active pre-checkout authorization per intent and `(bot/account, native query/update ID)`. Reuse with changed canonical business payload is a conflict. A different operation key does not bypass an existing active attempt, known ready link or payment authorization.

1. **Preflight, no network.** Verify recent signed Telegram identity; current canonical User is active and has actual advertiser profile/own order; country is actually published RUB, order is v1/NEW/uncaptured, approved terms/client allowlist/due are valid, core and new-order gates are enabled, bot/provider token and stable payment account are configured. Missing provider config must not first leave a new capture intent. Preserve the direct honorarium exclusion and standard50000/120000 components.
2. **Prepare/claim transaction.** Lock current User first (NO KEY UPDATE), then advertiser/actual order coordination and order, payment and checkout rows in a consistent order. Call the existing capture `issue` in this caller transaction; derive integer prices from its frozen intent/items, not mutable UI totals or legacy tariffs. Store the immutable request fingerprint, invoice DTO hash, configured account identity and a durable creating attempt/lease before commit. Foreign keys back to User are satisfied while that User lock is held. No wallet or grade/history snapshot is needed for invoice preparation.
3. **One-shot network operation, no open transaction.** Send prepared data through the dedicated link gateway. Do not use `TelegramMessengerClient._with_retry`, which retries network errors. Use a server-owned localized nonempty title/description within native limits, ASCII order UUID payload (preserves current native capture parser), exact positive integer RUB minor prices summing to the frozen total, existing receipt provider_data/email settings, no tips/shipping/Stars reinterpretation. Provider credentials remain inside the adapter/configuration.
4. **Persist result transaction.** Lock only the existing checkout/attempt projection; append its result/proof and CAS against the claimed attempt. Do not acquire new User/profile/wallet locks or insert User FKs here. A returned link is not exposed until this commit succeeds. Known rejection is failed; timeout/disconnect/crash/invalid provider result or uncertain result commit is unknown. Recovery expires a creating lease into unknown, never blindly sends again. Late results remain auditable and cannot overwrite a newer active attempt.
5. **Replay/read.** After current authenticated ownership is established, recognize the original request before applying NEW/uncaptured gates for a fresh sale. Exact duplicate request returns the persisted attempt/link and current actual capture state with no new provider call, even after payment. A ready link remains the same historical result; a pause disables new remote creation/open actions without destroying it. Polling never creates/retries an invoice. Already-issued paid receipts are still accepted through trusted ingress during pause.

Unknown `createInvoiceLink` is a lost nonmonetary result, not a charge retry. Once the single-active pre-checkout gate below exists, an explicit user retry may append a new link attempt for the **same frozen intent**, even when an older link's creation result is unknown. All links still encounter the same one-charge authorization. Preserve the older unknown outcome honestly. No browser callback, key change or invoice retry authorizes another payment after authorization uncertainty. A historical capture intent without a tracked checkout attempt is `untracked`; do not invent whether its old bot invoice was delivered. Adopt only with a concrete safe issuance decision under the shared coordinator.

## Before the user can be charged

The v1 pre-checkout branch resolves authenticated Telegram payer to the current canonical User and requires exact original client ownership. It loads the server order/issued intent/payment and verifies provider account, RUB amount, original payload, quote identity, uncaptured payable state and any existing authorization. No browser field or current legacy pricing contributes to this decision.

Acquire User→order coordination/order→payment→checkout/authorization locks, atomically append the approved query and occupy the unique authorization slot, then commit **before** `answer_pre_checkout_query(ok=True)` I/O. Identical query replay returns the same business decision; a second different query cannot acquire the slot, including two concurrent queries received before any successful-payment message. Bounded DB waits must leave enough time to reject within Telegram's10-second deadline; no provider-status call runs while holding those locks.

After approval or uncertain delivery of approval, retain that authorization until the corresponding captured receipt or a trusted provider/native outcome establishes disposition. Browser `cancelled`/`failed`, a disconnected Mini App, wall-clock TTL and absence of a webhook are not proof of failure and cannot free the slot. A failed payment may therefore need actual provider reconciliation or a reasoned reviewed resolution before a different query can be authorized. Expose this truthfully; no invented automatic expiry guarantee. Supporting a trusted failed-outcome/reconciliation workflow is a rollout prerequisite for usable recovery, separate from harmless link-creation retry.

## Durable paid receipt and actual status

For an authenticated v1 successful-payment update, persist a minimal immutable inbox fact before webhook200: configured bot/account routing identity, Telegram update/query linkage if available, native payer identity, order payload, both charge IDs, exact currency/amount, Telegram message date and canonical payload hash. Do not infer a bank settlement time or store unnecessary provider contact/card data. A replay is idempotent; changed data under the same source identity is a conflict, never an overwrite. A persistence failure returns non-2xx. Polling/native handler entry must use the same durable intake and cannot bypass it.

The worker resolves the actual payer and calls the existing atomic `PaymentService.confirm_telegram_payment`/capture adapter. Preserve original owner/account/quote/receipt checks and exact receipt replay. Do not call `calculate_invoice_data` after payment, reopen sales gates, recalculate mutable tariffs or drop a real receipt because its user is now blocked/paused. Ownership/account mismatch is retained unresolved for review; it never grants money to a different owner. Capture, allocations and snapshot outbox remain one caller transaction with the existing history barrier ordering. Notifications/moderation are after committed capture and have independent durable retry/deduplication; send failure does not erase the paid fact or charge again.

Status is an own-order transactionally consistent read. `confirmed` requires the actual immutable capture event/receipt matching the issued intent and stored payment/allocations; mutable `order.status` or `payment.status=paid` alone is insufficient. Return the original captured fact even if later business state changes, with any authoritative correction separately represented by its own source. Missing/inconsistent proof returns unavailable. Never infer a refund, publication, service fulfillment, commission availability or payment absence from checkout callbacks/projections.

## URL and Mini App behavior

Validate the provider-returned URL on the server before persisting a ready result and again before host opening: absolute HTTPS, exact ASCII host `t.me`, no credentials, unexpected port, query, fragment, control characters, backslashes, encoded path separators or arbitrary redirect. Allow only one nonempty bounded invoice slug in `/$<slug>` or `/invoice/<slug>`; reject ordinary bot/profile/HTTP links. The strict slug grammar/length is an application allowlist, not an invented provider guarantee; actual returned examples and tests must confirm it before rollout. Do not fetch/follow the URL server-side.

An explicit Pay action requests/reuses the stored checkout and opens a ready validated link through Telegram `WebApp.openInvoice` only when actual SDK capability is present. Cancel/failed/pending/paid callbacks all invoke the same signed status refresh. No callback posts payment success or changes ledger state. Disable duplicate open actions while the invoice is open; after reload read status first and never reopen or reissue automatically. An older Telegram host can offer a user-clicked `openTelegramLink`/safe same-link fallback; preserve the old bot payment path for legitimate legacy orders.

Bound polling after native close, for example immediate then1/2/4/8/15 seconds and stop; these intervals only bound UI refresh, never payment authorization. Stop when hidden/unmounted, session expired, proof confirmed or bound reached. Keep an explicit Refresh action afterward. Pending remains pending when no authoritative receipt arrives. Five locales,320px light/dark, safe DOM and existing native Back/MainButton behavior continue. Published refund duration/terms remain visible without a computed payment-based anchor or maturity promise.

## MAX identity and Task9f next stage

The real existing bridge is `bot/max/handlers/blogger_registration.py`: for an existing Instagram profile, a verification code stores actual MAX sender/chat metadata. `InstagramVerificationService.verify_code`/`verify_code_by_instagram_sender` confirms the code/profile, then `_try_link_max_account` calls `UserRoleService.link_max_account` and updates that existing canonical User's `max_id`. It is a creator Instagram-verification workflow; it is not a general advertiser account linker. The low-level linker must not become a public unverified checkout action.

`MaxMessengerClient.send_invoice` explicitly raises unsupported. For an actually linked owner, signed MAX status may return a server-built configured-bot handoff to the same order. User clicks MAX `openLink`; Telegram authenticates its own actual sender, resolves the same internal order owner and uses the shared v1 coordinator. A different Telegram account fails ownership. A MAX-only advertiser receives a precise linking-required state, never a made-up Telegram ID, copied authority, reassigned order or native MAX invoice claim.

Task9f must close that general identity gap, without expanding9e now: signed MAX owner initiates a single-use cryptographically unpredictable expiring nonce, stored hashed and scoped to that canonical owner. Target Telegram authenticates natively; explicit confirmation by the initiating owner binds the presented identity, with atomic unique consumption, rate limits and audit. Do not use the ordinary auto-register resolver to create a conflicting Telegram canonical account during the proof step. Attach only an unbound target identity to the same owner after both proofs; refuse conflicting existing canonical accounts/identities or money-history ambiguity. Never silently merge accounts, move orders, wallets, referrals or old money. An already-existing conflicting Telegram account requires a separate reviewed resolution rather than automated checkout account merge. Nonce expiry is only link-proof expiry and makes no claim about payment finality.

## Implemented scope and verification

The implementation and exact RED/GREEN evidence are recorded in `/tmp/umc-full-sprint-reports/task-9e-report.md`. `CheckoutService` owns issuance, explicit link retry, current own-order status and native one-active authorization. `PaidReceiptProcessor` owns durable authenticated receipt intake and replayable capture; notifications have a separate durable attempt/result worker. Protected signed current-admin review requires reason, evidence reference, expected version and authorization ID. It is explicitly manual evidence, and any matching paid inbox receipt blocks authorization release.

The production webhook commits the native paid inbox before HTTP acknowledgement and returns HTTP503 if persistence fails. The native dispatcher handler shares this durable inbox seam; real aiogram startup/shutdown hooks own the receipt and notice worker. This repository has no polling runner. Offset acknowledgement policy of an external polling runner is unverified and is not guaranteed by these hooks.

Telegram's original authenticated `message.date` remains the payment occurrence timestamp throughout delayed processing. A pre-due payment can be captured after the deadline, sales pause or account blocking; an actual post-due payment is retained unresolved. No due extension, refund anchor or provider outcome is inferred. Fresh link attempts and native precheckout reject expired due dates.

MAX uses only an actual stored canonical Telegram binding for a server-generated bot handoff. Advertiser-only accounts without such a binding require Task9f; no numeric-ID inference or automatic account merge is added. Provider/legal configuration and external payment operation remain subject to the separately pending approvals, with all finance flags unchanged and no live provider calls performed.
