# Task 10 / M02: moderated campaigns to an owned creator network

Status: proposed design for root review, 2026-10-23. Production code remains frozen during the shared full-suite run. This document is the only change authorized for this research stage. No migration, transport construction, runtime enablement or message send has occurred.

## Source and completion boundary

The canonical source is `docs/product/UMC-developer-sprint-2026-10-22.html:293` (M02), plus Task 10 in `docs/superpowers/plans/2026-10-23-umc-product-sprint.md:114`. M02 requires choosing a segment of the manager's own invited creators, UMC moderation, consent and limits, delivery to registered creators with a working Telegram bot, and actual delivery/response reports. Arbitrary recipients and contact exports are forbidden.

This stage includes the configuration and consent paths needed to make that flow usable. A permanently unavailable policy gate or an approval button without a worker does not finish M02. P02 subscriptions, paid pilot evidence, prices and A01 marketing attribution remain separate tasks. Neither this source nor the parent plan supplies numerical campaign quotas, so this design does not invent them.

## Findings in the existing application

- `application/services/manager_service.py:212` defines a manager through a `manager_orders` association. `is_manager_for_order` authorizes an exact order; creator assignment is narrower still. `miniapp/api.py` also shows the manager UI to administrators. These are operational order assignments, not ownership of a referral network.
- `infrastructure/db/models.py:938` stores the canonical direct network in `user_referral_bindings`: one registered user has one referrer. Pending invitations live separately. The own-only partner cabinet already uses this relation and is available to every account role. An advertiser, creator or operational manager can therefore own a network independently of staff assignments.
- A canonical registered creator has a blogger profile with `confirmed = true` and a nonblank canonical `instagram_user_id`. The unique verified-identity constraints prevent one current Instagram identity from counting as multiple creators. Pending referrals, unconfirmed profiles and the owner themself are not recipients.
- `agreement_confirmed_at` on blogger/advertiser profiles records the existing registration agreement. There is no campaign-purpose consent or unsubscribe record in the inspected application, domain or database code. An invitation, an Instagram check and a data-processing agreement cannot be treated as campaign consent.
- `UserStatus` includes active, pause, blocked, bot_blocked and deleted; users have server-stored `telegram_id`, `max_id` and language. Telegram `/start` can restore bot_blocked to active. A profile's Telegram social URL is a public profile field, not a bot delivery address. A stored Telegram ID plus active status is evidence of an eligible known bot contact, not a guarantee that the next request will be accepted.
- `creator_social_accounts` stores normalized public URLs, per-network work format and optional observed metrics with source/time. Only the canonical Instagram identity is verified. Other social links remain self-reported; unknown followers stay unknown. The partner adapter already checks the metric's canonical Instagram identity before exposing it.
- `ContentModerationService` provides a banned-keyword check. The Telegram order moderator separately resolves the actual user and checks `user.admin`. The keyword check is useful screening, but neither that check nor an order's approval approves a new campaign.
- `infrastructure/messenger/notice_receipts.py` already implements a single-request Telegram receipt transport. It accepts the structural `ReceiptMessage` protocol from `application/notice_delivery_ports.py`, returns a real `chat_id:message_id` provider reference, and reports missing receipts or network ambiguity as uncertain. The generic `MessengerClient.send_text` retries and returns no receipt, so it is unsuitable here. MAX transport exists, but M02 delivery stays Telegram-only.

### Concrete role ambiguity and proposed resolution

The product says “manager's own invited base”, while code uses “manager” for an order assignment. Granting campaigns from `is_manager` would admit staff without an owned audience and exclude other accounts with their own referral network. Granting access to an order's entire creator list would violate M02.

Proposed resolution for review: introduce an explicit, audited `campaign_publisher` grant issued to an existing account by a current active UMC administrator. That account can target only its own direct registered network. The grant does not create staff authority, network ownership, subscription payment or pilot evidence. Existing creator/advertiser/manager roles remain intact. Administrators may grant or revoke this capability through the actual configuration screen; staff assignment and a client-submitted role boolean never confer it. An empty own network remains honestly empty.

This is a proposed capability interpretation, not a claim that the source already defines a new business role. Root should approve this interpretation before implementation. No user question is needed to establish the current code facts.

## Concrete user flow

1. A current active UMC administrator opens the campaign administration screen in either Mini App. They enter required positive limits, the full localized consent text and version, the campaign review/dispatch validity durations, and the allowed filter/metric-freshness policy. The server validates and stores a draft; a distinct publish command appends the immutable published policy. Missing required values block publication with named validation errors. No unlimited or zero-as-unlimited values are accepted.
2. The administrator grants campaign publishing to an existing owner account with an auditable reason and optional expiry. Revocation takes effect for future preparation immediately. This is a nonmonetary capability, with no implied subscription purchase.
3. A creator opens “Messages from my inviter” from profile/settings in either host. The server resolves the creator's actual current direct inviter, displays that inviter's safe public label, and shows the current published terms in full. The default is unsubscribed. An explicit “Allow tasks from this inviter” command records the authenticated creator's own consent to that exact owner and terms version. No campaign is sent to request this consent. A permanent “Unsubscribe” action and a Telegram `/campaigns` settings entry open the same real screen.
4. The owner opens “Campaigns” from the partner cabinet in Telegram or MAX, sees actual policy limits and remaining measured/reserved capacity, and creates a task with title, text and optional safe HTTPS product/reference link. The screen explicitly describes a campaign invitation; it does not claim a paid order, manager appointment or creator reward.
5. The owner selects supported profile/social filters. Preview returns aggregate counts and exclusion reasons from the own network, without contact addresses or a base export. An empty or unavailable source is distinguishable from zero matching recipients. Submission creates a sealed content revision, policy reference and server-generated recipient-source snapshot.
6. A different current active UMC administrator opens the review queue. They see the exact submitted text/link, segment, audience count, consent/policy references, eligibility breakdown and screening matches. They approve or reject that exact revision with an auditable reason. There is no automatic approval. Approval revalidates the frozen candidates, reserves capacity and creates immutable per-recipient delivery jobs in the same transaction. It may remove now-ineligible recipients; it cannot add recipients who were absent from the submission snapshot. The approved audience and content have their own digest.
7. The bounded worker prepares and commits an actual attempt, rechecking ownership, consent, grant, current moderator authority, policy, status and Telegram contact. It then sends once outside all database transactions. The Telegram message includes the task, sender label, and one real native Web App action opening `?campaign=<campaign UUID>`. That screen shows the task with “Interested”, “Decline” and “Unsubscribe from this inviter”. It is implemented before any launch button can be sent.
8. The owner sees actual queued, preparing, provider-accepted, failed, unknown and skipped counts, plus distinct explicit interested/declined/withdrawn responses. Reports never label provider acceptance as read, interested, order acceptance or money earned. Unknown sends remain unknown even if a later genuine response arrives; that response is reported independently.

## Authority, audience and privacy

Every Mini App request uses the existing strict signed principal resolver, including freshness and duplicate-field checks. The resolved UUID is authoritative. Request schemas forbid extra fields, recipient IDs/address lists, owner overrides, moderator flags, consent booleans and policy-approval fields. Commands contain action-specific intent and expected versions; the service obtains all authority and factual references from persisted current state.

An eligible recipient must satisfy all of the following at submission, approval and preparation: direct `user_referral_bindings.referrer_user_id == authenticated owner`, not self, canonical confirmed creator, current active status, a usable positive private Telegram bot ID, and unrevoked explicit consent to this owner under the applicable published terms. Deduplicate by current canonical identity and actual Telegram destination as well as recipient UUID. A Telegram social link, MAX chat or address in task text never supplies a delivery destination. MAX-only creators are excluded with a truthful aggregate reason; their manager can still manage a campaign from MAX.

Initial filters are a typed allowlist of existing server-owned data: profile country/region/city, topic identifiers, profile work format, presence of an attached supported social account, that account's work format, and observed follower thresholds for a selected network. Country/topic values come from existing lookup sources. Unknown metric values fail a numeric threshold rather than becoming zero. Metric eligibility requires source/time, matching canonical identity where applicable, and the published freshness rule; the UI explains this exclusion. This stage does not infer cross-network verification, private audience demographics or reach from profile averages. Legacy price and currency values are not silently converted into new campaign filters.

Owner reports contain task content, aggregate delivery facts, and paged safe creator/public-social labels plus explicit responses from this campaign. They exclude Telegram IDs, phone numbers, private contact fields and raw provider errors. Nonconsenting members appear only in aggregate eligibility counts. No CSV/contact-export route exists. Recipients see only their own task/consent/response; one recipient cannot enumerate the audience. The moderator sees the information needed to review a task and its provenance, not a downloadable address list. The same owner restrictions apply to an administrator using the owner UI.

## Persisted policy, limits and configuration

Create a campaign policy independent of financial pricing. Publishing requires an actual active administrator and stores version, published/effective timestamps, full localized terms plus content hash, publisher, reason, enabled/suspended state and required numeric settings. A signed admin command screen performs create, validate, publish, suspend and supersede operations; raw CRUD cannot rewrite published history. The owner and recipient read APIs expose the relevant published text/version and actual limits. A missing policy is a clear setup state with an administrator path, not a permanent hard-coded unready gate.

Required administrator-supplied limits cover: recipients per campaign; submissions and active campaigns per owner over an explicit UTC accounting window; attempted deliveries per owner and globally per window; cross-owner per-recipient frequency/cooldown; message/title/link size; review and dispatch expiry; and worker claim batch/concurrency and start rate. Values and window durations are mandatory, bounded positive integers where applicable and published as actual configuration. Technical transport size constraints are validated independently. The source supplies no numbers, so no numeric quota defaults will be invented in code, examples or tests that imply a product promise. Tests use clearly synthetic configurations.

Approval reserves recipient capacity atomically against the actual window counters, so concurrent approvals cannot oversubscribe. Attempt start consumes the reservation; every started attempt, including failed or unknown results, counts toward send/frequency limits. Unstarted skipped/cancelled work releases only its unused reservation. Existing attempted usage remains auditable across policy changes and campaigns, and a new policy/version cannot reset window usage or recipient cooldowns. A stricter newly effective policy is rechecked before each start; work waits or is skipped rather than exceeding it. Never reserve an unbounded future audience. Expired campaigns stop new starts; cancellation cannot retract an already in-flight provider request.

Add a campaign-specific runtime flag, default off, which prevents both transport construction and worker sends. Published configuration and consent/settings/report reads remain usable while sending is paused. Actual admin publication/grant paths make the system configurable; enabling production delivery remains a separately authorized operational action. This implementation and its tests use offline transports only. Financial core flags, financial ledger and P02 entitlement activation remain unchanged.

## Model and application boundaries

Use a dedicated campaign queue/outbox rather than letting the generic financial or legacy publisher consume campaign events. Proposed new modules are `domain/campaigns.py`, `application/campaign_ports.py`, focused policy/consent/campaign/delivery/report services, `infrastructure/db/campaign_models.py`, `infrastructure/db/repositories/campaigns.py`, `infrastructure/memory_campaigns.py`, `miniapp/campaign_api.py`, and a campaign worker/runtime module. Split the SQL adapter by responsibility if it becomes too large. The schema revision is chosen with root only after the current fixture-head freeze is released.

Persist these facts with foreign keys, uniqueness/check constraints and append-only history guards:

- Published policy/terms revisions and their admin publication/suspension events; publisher grants and grant/revoke events.
- Consent events keyed by creator and exact owner, with terms version/hash, authenticated actor, occurred time, operation key and grant/revoke action. A versioned current projection supports atomic checks. Registration consent is never backfilled into this table. Revocation stays available even when publication/grants/sends are paused.
- Campaign owner and current version projection; immutable content/segment revisions; submission snapshots; current status; command receipts and events. A draft is saved through an explicit versioned command. Editing rejected/unstarted work creates a new revision and requires new submission/review. Content is sealed once dispatch starts; subsequent tasks are new campaigns subject to all limits.
- Recipient-source rows at submission: campaign/revision, recipient UUID, canonical identity reference, direct-binding provenance, applicable consent event/version, profile/social observation references, eligibility time and internal contact reference. Store the authoritative source, not a claimed ownership flag. New invitees after submission do not enter that review silently.
- Review records: exact submission/revision/content and recipient-set digests, reviewer UUID, decision/reason/time and policy reference. Approval binds a concrete surviving subset of submitted sources, current quota reservations and queue rows in one committed transaction. Expected-version/unique-decision guards stop double approval and stale reviews.
- Quota reservations/usage events and projections, with explicit scope/window/idempotency references. No financial obligation, synthetic payment, wallet write or subscription-price record is created.
- Delivery jobs referencing the exact approved source/review; immutable attempts with lease, prepared text/localization, action URL/label, actual stored Telegram destination and provenance; immutable provider outcome records. A campaign attempt implements `ReceiptMessage` directly. It does not construct a financial NoticeAttempt with dummy IDs.
- Response events for the authenticated approved recipient, campaign revision and response intent; current response projection with optimistic version. “Interested”, “declined” and “withdrawn” are explicit user actions. Replays do not add respondents. They neither assign an order nor create consent, delivery receipts or financial outcomes.

State transitions are explicit: draft → submitted → approved/rejected → dispatching → completed, with cancelled/expired/stopped outcomes retaining history. Delivery totals derive from unique approved jobs and their latest actual outcomes, not optimistic subtraction. Response totals derive from current distinct respondent state, retaining change history. Report reads use one coherent database snapshot and state their observation time.

## Worker protocol and concurrency

1. Claim only this campaign's dedicated ready queue rows under a bounded batch/lease. Validate immutable source/review links and lock campaign/job plus quota/consent projection rows in a documented common order. Re-read current owner grant/status, exact direct binding, creator identity/status, consent, reviewer active-admin status, published policy, expiry and Telegram contact. Never acquire financial wallet/item locks.
2. If obsolete, revoked, expired, paused or over current limits, append a safe skipped/deferred reason and update the projection without inventing a send. If ready, create the exact immutable attempt and consume the appropriate reservation/start counter. Persist and commit before returning the detached message DTO. Do not keep a session/lock open across transport work.
3. Perform one receipt-transport send outside the transaction. Localized body and the native action fields come from the prepared attempt, not parsing translated text. Reuse the existing single-request Telegram adapter with its real provider receipt contract. No generic retry wrapper or MAX fallback is permitted.
4. In a fresh transaction, append the actual accepted/definite-failure/unknown outcome associated with the original attempt/lease and update only the matching current job. A late result stays attached to the original attempt and never rewrites another campaign/revision/recipient. Recheck current state for projections; a concurrent cancellation or unsubscribe does not erase a real transport outcome or authorize another attempt.
5. A stale prepared/sending attempt is recovered as unknown, even if a crash might have occurred before network I/O. Unknown results never automatically resend. A definite rejection may be retried only through a current active administrator's explicit reviewed command with reason, fresh eligibility/limits and a new audited attempt; unknown results have no resend command in this stage. No capacity is restored merely because a send failed.

Consent/cancellation have a defined in-flight boundary: revocation committed before preparation prevents the attempt; preparation and revocation serialize on the current consent projection. After a committed attempt starts, a concurrent unsubscribe can only prevent later attempts, because the provider request cannot be atomically cancelled. The UI confirms unsubscribe for future messages, and audits preserve the actual ordering. Recheck immediately before preparation and keep preparation-to-send short; do not claim an impossible no-race guarantee or hold a database transaction during I/O. A known blocked-contact result suppresses future campaign starts for that contact until an actual authenticated Telegram interaction establishes reachability again; no test send is used as a probe.

## API and Mini App design

Mount the signed router through the existing API factory so both real ASGI apps use it: `/miniapp/api/campaigns` on Telegram and the existing `/api` alias on MAX. Use POST signed reads consistently with current private Mini App APIs. Exact route suffixes are grouped as policy/settings, owner list/preview/draft/submit/cancel/report, recipient view/respond/unsubscribe, and admin policy/grant/review/retry. Each command carries an operation key and expected version; duplicate keys with changed intent conflict. Unauthorized IDs return scoped forbidden/not-found responses, and extra query/body targeting fields are rejected. Read responses include actual server capabilities and current versions, not JavaScript role decisions.

Create `miniapp/umc-campaigns.js` with a `.umc-campaigns` CSS namespace and narrow mounts in both HTML templates. Reuse supplied fonts, colors, form/cards, focus states and host adapters. Owner flow: list → content and segment form → real aggregate preview → explicit submit → status/report. Recipient flow: inviter consent settings → task → explicit response and unsubscribe. Admin flow: required policy form/publication, existing-account publisher grants, review queue/detail and approve/reject forms. Screens show genuine loading, no policy/grant, no consent, empty segment, moderation pending/rejected, paused, partial delivery, unknown and retry states. Use textContent/createElement and validated HTTPS links; no injected HTML or address display.

Support existing Russian, English, Kazakh, Belarusian and Uzbek locale behavior, coherent fallback and server recipient language in Telegram text. Preserve both native back/main-button adapters and browser fallback. A MainButton represents only the active actual form action. Deep-link parsing is strict for one campaign UUID and respects existing assignment/selection/partner routes. Authenticated task lookup checks recipient membership; possessing the URL grants no authority. Unsubscribe remains available from the task/settings even when campaign response or sending is closed.

“Interested” is not an accepted paid offer. The report can show that actual response next to the owner's already-known public creator identity, without exposing a new contact list. This stage does not route interested creators into an order or send follow-up notifications; a future integration must have its own real workflow and consent/quotas.
