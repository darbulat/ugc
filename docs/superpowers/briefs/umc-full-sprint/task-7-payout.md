# Task 7 / P01 — reserve and reviewed manual payout

Status: proposed implementation brief for root review. Read-only source investigation; no payout code, schema, feature activation, bank operation, or actual legal approval is implemented by this document.

Sources: canonical HTML `docs/product/UMC-developer-sprint-2026-10-22.html` (financial-v1, P01 amendment, F01, operations, ACs); `docs/superpowers/specs/2026-10-23-umc-product-sprint-design.md`; `docs/superpowers/specs/2026-10-22-financial-ledger-adr.md`; sprint plan Task 7 and Task 13. P01 requires available-only atomic reservation, duplicate prevention, reviewed manual payout with bank reference/reconciliation, a queue handled within 72 hours, and a dispute stop. F01 adds real bank automation only after provider/access is supplied.

## Existing contracts to reuse

- `FinancialLedgerService.issue/record_maturity/transfer` and `SqlAlchemyFinancialLedgerRepository` already persist integer-minor immutable obligations, source snapshots, journal and replayable wallet projections. Existing `transfer` deliberately supports only lifecycle transitions; it does **not** authorize available→reserved, reserve release, or bank settlement. Do not widen its allowlist and treat arbitrary caller UUIDs as payout proof.
- `FinancialReconciliationService.require_ready(recipient_id, currency, *, session)` checks journal replay, issuance cardinality/amount, and wallet projection under its writer barrier. Its `payout_ready` explicitly proves consistency only, not legal permission, cash liquidity, bank readiness, or absence of a newly persisted dispute. Use it before and after new monetary mutations.
- `JournalMovement` has `request_id`, `allocation_id`, `execution_id`, typed actor, source/case/refund references and canonical idempotency. Reserve-related movements require request+allocation; paid requires execution too. Replay checks allocation binding and remaining reserved amount, and rejects paid without reserve. Paid history is never moved back; a later economic correction is a linked debt/case, and recovery is actual repayment.
- `WorkFinancialGuard.case_for_item/require_clear` reads authoritative immutable collaboration disputes under the held item barrier. It catches a dispute before financial outbox delivery. Payout must use it directly, not rely only on current wallet buckets or outbox status.
- `SqlAlchemyFinancialLedgerRepository.lock_recipients` and `lock_wallets` coordinate with legacy writers using sorted User **NO KEY UPDATE**, then recipient/currency wallet locks. Preserve the existing FK-compatible lock mode.
- `LegacyFinancialGuardRepository.assert_payout_allowed` is a durable legacy dispute stop, with no automatic release. It must remain effective alongside v1 readiness; v1 must not erase/import legacy balances or old case history.
- Existing signed MiniApp ingress uses `SignedMiniAppRequest` and `PrincipalResolver`; current active user/admin must still be loaded inside the command transaction. A signed body, persisted actor-kind string, legacy admin callback, or client boolean is not role authorization.
- Existing financial gates are independent and false by default: `FINANCIAL_CORE_ENABLED` and `FINANCIAL_PAYOUTS_ENABLED`. Keep both required for new payout mutation; reading own existing history may remain available while paused, with current access checks.

## Storage gaps and migration hazards

### Actual existing payout request

`PayoutRequestModel` (`infrastructure/db/models.py`) is legacy storage:

- `request_id UUID` primary key; `user_id` FK to users with **ON DELETE CASCADE**;
- requested/updated timestamps, status enum `pending/paid/cancelled/deleted`;
- nullable decimal `amount Numeric(10,2)` and currency default RUB;
- no minor-unit authoritative amount, operation key/hash, versioned approval, requisites snapshot, allocation, execution, bank reference, or 72-hour audit.

The journal currently has a real `request_id → payout_requests.request_id` FK. Its `allocation_id` and `execution_id` are merely nullable non-nil UUID columns: **no payout allocation or execution tables/FKs exist**. `payment_item_allocations` are immutable customer capture components and must not be reused as payout allocations.

Migration `0032_payout_requests_index_and_one_per_day` creates unconditional unique `(user_id, UTC requested date)`. Migration `0079` adds partial unique `(user_id,currency,UTC date)` except cancelled/deleted, but never drops the older index. Full migrated schemas therefore retain the stronger older rule too, including across currencies and after cancellation. Metadata-only inspection of the newer ORM index misses this. Neither daily restriction is a P01 monetary/idempotency authority.

`PayoutRequestAdmin` is already read-only. However Telegram/MAX legacy referral callbacks still invoke `SqlAlchemyPayoutRequestRepository.update_status(...PAID)` without bank proof. The repository also supplies legacy paid totals used by legacy referral statistics. A v1 row must be excluded from every such legacy read/write path, or the old callback can claim payment and old totals can subtract v1 money again.

### Recommended compatibility decision for root

Reuse a legacy request row only as an immutable identity anchor, so the existing journal request FK stays real. Add an explicit nullable **payout protocol discriminator** (`payout_protocol`), separate from arbitrary policy-version labels: legacy NULL, a published v1 protocol marker for new requests. New immutable v1 request authority and mutable v1 projection use the same request ID. The legacy parent anchor stays `pending`; v1 status/amount authority comes from new facts and never from that enum/decimal field.

Recreate **both** legacy daily indexes with a legacy-only discriminator predicate, preserving their existing legacy behavior while excluding v1. Do not silently import daily limits into the new product. The v1 double-spend protection is canonical command idempotency plus locked available allocation; separate legitimate requests cannot reserve the same units. Filter the legacy request repository/list/paid-total/update-status paths to legacy-only, and explicitly reject v1 IDs in legacy callbacks. Keep generic admin CRUD read-only. Add a DB immutability guard for v1 parent anchors so direct legacy status/recipient/amount/delete changes fail.

New immutable v1 request/user FKs must use NO ACTION/RESTRICT, with no cascading deletion of financial/evidence facts. Even though the old parent has a User cascade, the new child/user references and immutability guard must prevent deleting a v1 anchor/history. Preserve ordinary legacy deletion behavior where no financial history already prevents it.

Root alternative: retain the legacy daily restrictions explicitly for v1 and present that as a reviewed product limit. This is simpler DDL, but it changes P01 behavior and still requires all legacy route/statistic separation. Recommended design is the explicit discriminator.

## Proposed new application boundary

New files, with no bank calls in transactions:

- `application/payout_ports.py`: frozen command/result/read DTOs, readiness/requisites/bank evidence ports and repository protocol.
- `application/services/payout_service.py`: authenticated request/review/reject/start/settle commands. It owns coordination and calls narrow persisted payout ledger primitives; it never issues entitlement or recomputes rates/grade.
- `application/services/payout_read_service.py`: own-only history and protected admin queue/details, consistent snapshot reads and masked destination by default.
- `infrastructure/db/payout_models.py`, `repositories/payouts.py`, and `memory_payouts.py`: immutable facts plus replayable projection; metadata hook and a migration following the actual then-current head, coordinated with root.
- `infrastructure/secure_requisites.py`: actual authenticated encryption adapter behind a small encryption port, configured with an externally supplied key/key identifier; no default/fallback key.
- Separate `miniapp/payout_api.py` and container/scheduler integration only after root coordinates ownership. Legacy notification and callback routes must not become v1 proof paths.

Candidate public application interfaces (final naming can be settled during review):

- `request(PayoutRequestCommand, *, session) -> PayoutState`: server actor ID, stable operation key, positive `amount_minor`, RUB, own server-owned requisites/terms references. No caller recipient ID, allocation list, balances, approval flag, tax rate, or bank execution ID.
- `review(PayoutReviewCommand, *, session) -> PayoutState`: actual current active admin, request ID, expected version, stable key, reason and protected evidence reference; verifies applicable stored recipient/payout requirements. Review approval reserves no additional money and proves no bank transfer.
- `reject(PayoutRejectCommand, *, session) -> PayoutState`: current admin, version/key/reason. Releases only a safe unstarted reservation; it cannot release an in-flight/unknown payment.
- `start_manual(PayoutStartCommand, *, session) -> PayoutExecutionIntent`: final current readiness check, immutable prepared intent/fence, frozen exact recipient/amount/requisites/proof. Commit before the human acts in the bank. One live execution per request; no generic status change substitutes for this step.
- `record_manual_result(PayoutManualResultCommand, *, session) -> PayoutState`: current admin, expected version/fence, actual protected bank evidence, bank account/reference scope, actual settled amount/currency/time, reason. Only an actual reviewed settled bank record can consume reserve. Failed/unknown evidence is also retained and never silently retried or unreserved.
- `get_for_actor(request_id, actor_id, *, session)` / `list_for_actor(actor_id, *, session)`: own request only; current actual admin has explicit protected review access. No universal manager view or recipient spoofing.
- `list_queue(*, as_of, limit, session)`: immutable requested time and `requested_at + 72 hours`, oldest/overdue first. A timer creates a deduplicated escalation fact/outbox notification; it never marks paid, releases reserves, or restarts the 72-hour clock.

## Proposed facts and constraints

- `financial_payout_requests`: immutable request identity/scope, recipient/currency, positive minor amount, actual requested_at, deadline exactly +72h, operation key/canonical hash, frozen requisites version/fingerprint and accepted applicable terms references. One request has one currency. No invented fees, minimum, deduction, or expiry.
- `financial_payout_allocations`: immutable allocation ID, request, obligation, recipient/currency, positive reserved amount and initial reserve movement reference. Unique request/obligation; composite scope FKs to request and obligation. Allocations split a wallet request across real available obligation balances in deterministic order and retain that exact source forever.
- `financial_payout_events`: append-only versioned create/review/reject/block/start/result/escalation facts with actual actor/server clock/reason/evidence, operation key/hash and unique `(request_id,version)`. Repeated identical command returns original; changed payload conflicts and is audited outside the rolled-back transaction.
- `financial_payout_states`: replayable current state/version/block/fence projection; never sole money authority. Suggested states: reserved, approved, blocked, executing, unknown, paid, rejected. Reopening an unknown or blocked outcome is a separate versioned evidence-based review.
- `financial_payout_execution_intents`: immutable prepared exact scope/fence before external action. Attempts and actual outcomes are distinct. Unknown remains a first-class observation, not permission for another transfer.
- `financial_payout_executions`: immutable reviewed actual settled bank fact, exact request/recipient/amount/currency/requisites fingerprint, actual bank/account reference namespace, protected evidence identity/hash, observed/settled times and admin attestation. Unique request for the initial full-settlement MVP and globally unique actual bank reference in its authoritative bank/account namespace. An arbitrary channel prefix must not allow the same transfer to pay two requests. No case-folding/canonicalization beyond the selected bank's actual reference contract.
- `financial_payout_execution_allocations`: immutable binding of the actual execution to each reserved allocation/obligation/currency/amount. Composite FK from new paid journal rows binds these facts, not just non-null UUIDs.
- `financial_recipient_requisites` (versioned encrypted immutable snapshots) and protected evidence/read-access audit. Raw payload never enters command audit JSON, journal reason, logs, outbox, bot text, partner aggregate response or source hash exposed publicly. Store key ID, nonce/envelope metadata and masked label/fingerprint; encryption authenticates record recipient/version context. Replacement makes a new version and never changes a prepared/settled destination.

Extend journal reference enforcement through new composite allocation/execution FKs and paid/reserve consistency guards. Existing immutable rows may already contain foundation-era UUID references without corresponding payout facts; **do not fabricate parents, backfill, rewrite or delete them**. Audit first. A migration may use NOT VALID FKs that enforce new writes but leave old history unvalidated, with an explicit unresolved-history readiness stop; validate only after real evidence resolves it. SQL checks must explicitly reject NULL where required; a nullable expression passing a CHECK is not proof. Freeze new schema definitions per migration rather than importing later-mutated live tables.

## Coordination and monetary transitions

Discover immutable request/obligation scopes first. Lock sorted **all actor/recipient User rows → sorted recipient/currency wallets → needed order/payment coordination rows consistently → sorted paid items → sorted obligations → sorted requests**. Re-read scope after locks; if a new recipient is discovered, roll back/retry the whole transaction. After item locks, do not call helpers that discover/acquire additional User or wallet barriers. Append journal/projection changes only through a primitive whose complete scope was already locked; bank/S3/bot I/O stays outside the transaction. Re-locking already held barriers must not hide a helper discovering additional recipients. Payout does not need to lock creator profile/history or recalculate historical qualification.

Before a new reserve or execution: current actor/ownership/role; both feature gates; applicable stored requirements; replay/issuance/projection consistency; each source obligation's available/reserved balance; current item/refund/case truth including WorkFinancialGuard; unresolved legacy stop; and current request/fence/version. The ledger `payout_ready` flag alone is insufficient. Wallet debt and unmatched historical execution are surfaced explicitly; no automatic debt netting or manager future offset is authorized.

Root decision needed: until a reviewed debt policy exists, recommend failing a new request/execution closed for unresolved recipient debt with a specific manual-review reason, while preserving available funds unchanged. This is a proposed conservative gate, not a claim that P01 already specifies a global debt-forfeiture or offset rule. A dispute on another person's/unrelated ground must not be invented as a universal block.

- Reserve: allocate only real available obligation units; append available→reserved movements with actual request/allocation IDs; insert immutable allocations/events and update wallet/request projections in one caller transaction. Reconcile after mutation. Two concurrent requests cannot reserve the same units.
- Reject before execution: append linked reserved→available releases only for current clear grounds. A disputed allocation cannot be released into available merely because a request was rejected. It stays blocked/reserved for review or moves reserved→blocked through a separately reviewed case-linked transition. Unknown/in-flight bank outcomes never release automatically.
- Dispute after request: record an immutable request/allocation case link and block the **related payout** immediately on authoritative re-read, even if the dispute outbox lags. Retaining money in reserved with a blocked request is safe; a mutable request flag without the case history is insufficient. A multi-allocation manual transfer may be stopped as a whole until review; unaffected funds are not erased.
- Actual paid: consume each frozen allocation reserved→paid and bind actual execution proof. Same command/reference replays once. A stale role, changed amount/destination, fake pointer, duplicate bank reference, unknown result or unmatched proof cannot make a new paid movement.
- Physical settlement received after a dispute/cancellation attempt is **retained**, not discarded to make the projection appear safe. It becomes an exceptional actual bank fact under review; historical paid must remain truthful. An unknown payment cannot have been unreserved. Any economic cancellation after paid opens linked debt/case via the correction coordinator, never paid→available.

Manual banking cannot make the check→human transfer interval atomic with a later dispute. Prepared/started intent and frozen reserve prevent two operators or an unknown retry from spending twice; current recheck blocks an unstarted transfer. A dispute arriving after an actual external send requires recorded outcome/reconciliation/manual review. Do not hold SQL locks across a human bank session or claim a stronger physical guarantee than this protocol provides.

## Privacy, legal and external inputs

Source inspection found no bank requisites schema, encryption/key-management configuration, authenticated evidence blob store, or recipient legal approval process. `cryptography` is installed but is not configured security. Implementation can add a tested encryption port/adapter and reject writes/reveals when the actual configured key/storage is absent. Synthetic fixtures may supply ephemeral keys and visibly synthetic approval/proof facts; those do not activate production or prove external approval.

Recipient legal status/required fields, applicable agreements, permitted payout rails, withholding/reporting rules, authorized bank account/reference format, evidence retention/access policy and actual key custody remain external inputs. Store actual server-approved identity/reference/date and accepted terms once supplied; do not accept a public `approved=true` or invented default legal status. No automatic 6% deduction, fees, numerical minimum, 365-day forfeiture, or future manager offset. For this MVP, no-adjustment settlement must match the whole requested amount actually received; a different actual net/withholding is an exception requiring the later approved adjustment rules, not a guessed ×0.94.

F01 remains a separately selected provider adapter: actual authenticated transfer/status/reconciliation contracts, account scope, credentials, idempotency behavior and timeout semantics. The application can define typed prepared/status/accepted/failed/unknown ports and exercise synthetic boundaries now. It cannot call an unspecified provider, fabricate a bank reference/settled callback, or equate an HTTP timeout with failure. No provider integration is needed to build the safe reserve/manual-review/evidence workflow behind off gates.
