# Контроль доступа Meta и напоминания администраторам

`python -m ugc_bot.meta_token_monitor` — отдельный процесс только для
проверки двух доступов и технических уведомлений выбранным администраторам.
Он не обновляет токены, не собирает блогеров, не вызывает верификацию
и не пишет в рабочую базу. Существующие планировщики не переключаются.

## Сроки и типы токенов

- `verification`, `instagram_login`: один GET своего профиля на
  `graph.instagram.com/v24.0/me`. HTTP 200 подтверждает доступ, но не
  определяет дату истечения. Срок берётся только из подтверждённой записи
  выдачи/продления (`expires_in` вместе с временем ответа) либо из
  проверенных сведений Meta. Возраст файла, контейнера и предполагаемые
  60 дней не используются.
- `discovery`, `facebook_user`: GET `graph.facebook.com/v27.0/debug_token`
  проверяет приложение, валидность, необходимые разрешения и срок.
  Из положительных `expires_at` и `data_access_expires_at` выбирается
  более ранняя дата. Нулевые/отсутствующие значения не означают
  автоматически бессрочный доступ.
- Дата из настройки действует только при совпадении полного SHA-256
  токена с `expiry_fingerprint`. Замена токена без соответствующих
  метаданных вызывает предупреждение о неизвестном сроке.

Значения токенов, ответы с секретами и секретный JSON не сохраняются
в репозитории, логах, PR или сообщениях. Используются только фиксированные
HTTPS-адреса Meta и Telegram, без переходов по редиректам.

## Доставка

Проверка выполняется раз в час. При пересечении порогов 7 суток и
24 часа уведомление отправляется каждому явно настроенному админу.
При первом запуске внутри последних суток отправляется только срочное
предупреждение. Просроченный, недействительный, отсутствующий токен
и неизвестный срок обрабатываются отдельными предупреждениями.
Недоступность Meta не равна недействительности токена; об отсутствии
результата сообщается после трёх подряд неудачных проверок.

SQLite в отдельном постоянном каталоге хранит только отпечатки, сроки,
состояние проверок и факт доставки каждому адресату. Неудачная доставка
повторяется в следующем цикле, успешные адресаты исключаются из повтора.
После изменения срока, в том числе при сохранении строки токена,
пороговые предупреждения относятся к новому сроку. Старые недоставленные
события после продления не воспроизводятся.

Доставка имеет семантику at-least-once: авария между успешным ответом
Telegram и записью SQLite может привести к единичному повтору. Постоянная
блокировка файла предотвращает одновременный запуск двух экземпляров
на одном каталоге состояния. Каталог состояния нельзя удалять при
обновлении контейнера.

## Приватная настройка

`/settings/settings.json` (0600, родительский каталог 0700) имеет вид:

```json
{
  "bot_token": "<текущий токен бота>",
  "recipients": ["<admin-1-id>", "<admin-2-id>"],
  "tokens": [
    {
      "key": "verification",
      "purpose": "Рабочая верификация Instagram",
      "kind": "instagram_login",
      "token": "<текущий рабочий токен, без перевыпуска>",
      "expected_username": "usemycontent",
      "expires_at": null,
      "expiry_fingerprint": ""
    },
    {
      "key": "discovery",
      "purpose": "Тестовый доступ Meta Discovery",
      "kind": "facebook_user",
      "token": "<отдельный пользовательский токен>",
      "app_id": "1528779102424926",
      "required_scopes": [
        "pages_show_list", "instagram_basic",
        "instagram_manage_insights", "pages_read_engagement"
      ]
    }
  ]
}
```

`null` в примере — явно неизвестная дата, а не готовый контроль 7/1.
До появления подтверждённой даты для рабочего токена нельзя заявлять,
что предупреждения перед его истечением полностью настроены.

Список содержит от одного до трёх различных личных Telegram ID. Получателей
сверяют с подтверждёнными админами и текущими Telegram-профилями: сохранённое
в базе отображаемое имя может устареть. Пользователи, блогеры и менеджеры
не добавляются автоматически. Для уведомлений только двум операторам
в `recipients` оставляют ровно два подтверждённых ID. Исключённый адресат
не получает новые уведомления и повторы старых неудачных отправок.

При ротации рабочего токена сначала проверить новый доступ, затем
обновить приватную настройку монитора тем же токеном и подтверждённым
сроком. Датой нужно снабдить SHA-256 именно нового значения. Каталог
настроек монтируется целиком, поэтому атомарная замена JSON видна
контейнеру без перезапуска; новая настройка читается в следующем цикле.
Монитор не меняет токен в работающих приложениях.

## Выпуск и проверка

Дождаться CI и ревью, слить PR в main. Собрать новый образ из чистого
архива слитого коммита. Сохранить служебные каталоги вне dirty checkout
сервера, например `/home/deploy/.local/state/ugc-meta-token-monitor/`.

Передать в `docker-compose.token-monitor.yml`:

- `META_TOKEN_MONITOR_IMAGE` — образ слитого коммита;
- `META_TOKEN_MONITOR_SETTINGS_DIR` — закрытый каталог с настройкой;
- `META_TOKEN_MONITOR_STATE_DIR` — постоянный каталог SQLite;
- `META_TOKEN_MONITOR_UID` / `META_TOKEN_MONITOR_GID` — владелец каталогов.

Сначала выполнить `--once --dry-run` с теми же каталогами. Он делает
только проверки Meta, не отправляет сообщения и не меняет отметки доставки.
После проверки настроек запустить только `meta_token_monitor` с
`up -d --no-deps meta_token_monitor`. Compose-файлы и `.env` рабочего
проекта сохраняются; app/app_2/instagram_webhook не пересоздаются.

При лимите CPU 0,1 запуск Python-проверки может занимать больше 10 секунд;
таймаут healthcheck составляет 60 секунд, начальный период — 120 секунд.

Проверить health монитора, безопасный результат первого цикла и доставку
возникших технических предупреждений только настроенным админам. До и после выпуска
проверить health рабочих приложений и GET своего Instagram-профиля.

Откат: остановить только `meta_token_monitor`, сохранив его настройки
и SQLite. Рабочая верификация и сборщики не затрагиваются.
