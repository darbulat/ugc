# Диагностика и инвентаризация Instagram

Первый этап качества данных: увидеть причины отказов и измерить пробелы до
изменения очереди обновления. Рабочая верификация, подбор, токены, квоты и
ScrapeCreators этим этапом не переключаются. Миграций и новых рассылок нет.

## Диагностика планового Discovery

При отказе `Discovery attempt failed` содержит внутренний UUID профиля,
`provider_outcome`, результат записи `saved_outcome`, HTTP-статус, числовые
`meta_code` / `meta_subcode`, булевый `transient` и долю использования квоты.
Строковые/неправильно типизированные коды игнорируются. Текст ошибки, полный
ответ, URL запроса, заголовки и токены не сохраняются в событии.

`Discovery batch summary` показывает число завершённых попыток, результаты
и причину остановки. Неудача до завершения записи может уже расходовать бюджет:
источник истины для количества HTTP-попыток — `requests_used` в control-таблице.
Прерванный пакет получает `interrupted`, а не ложный `complete`.

Классификация и защитные остановки сохраняются: неизвестный `invalid_request`
по-прежнему останавливает пакет. По одному общему статусу нельзя объявлять
ошибку безопасной для пропуска профиля. Решение о пропуске требует кода Meta
и отдельной проверки. Потерянный подробный ответ старого запроса восстановить
из общего статуса нельзя; новые коды появятся у будущих плановых отказов.

## Отчёт без сбора данных

В окружении приложения с существующими `DATABASE_URL` и
`INSTAGRAM_IDENTITY_CONTEXT`:

```bash
python -m ugc_bot.instagram_data_quality_report --fresh-days 14
```

Команда работает только с PostgreSQL, в одной `REPEATABLE READ READ ONLY`
транзакции. Ожидание блокировки ограничено 1 секундой, каждый SQL-запрос —
15 секундами. Она не вызывает социальные API, не запускает планировщики,
не создаёт уведомления и не читает `instagram_stats.raw_response`.
Настройки подключения и тексты исключений в вывод не попадают.

JSON содержит только агрегаты:

- Все анкеты блогеров, подтверждённые анкеты, отсутствие Meta ID, статусы
  аккаунтов и недоступность бота с учётом журнала блокировок/разблокировок.
- Состояние метрик **по источникам отдельно**: подписчики основного Meta,
  подписчики/публикации старой статистики и Discovery; доступные поля Discovery.
- `missing`, `undated`, `fresh`, `stale`, `identity_mismatch`,
  `before_current_identity`, `invalid_timestamp`, `future_timestamp`.
  Состояния одного поля в сумме равны числу анкет; складывать разные источники
  как уникальных блогеров нельзя. Нулевые счётчики, false и известное пустое
  значение дополнительного поля не равны отсутствию данных.
- Пробелы города, тематик и географии ЦА. Это заполненность, а не проверенная
  достоверность. У ручных полей нет отдельных дат подтверждения; общий
  `blogger_profiles.updated_at` не используется как дата их актуализации.
- Число подходящих под текущие правила Discovery профилей, сколько из них
  ожидают попытки, результаты прежних попыток и сохранённый control-план.

`legacy_attempted_within_window` — только факт недавней попытки старого сборщика.
Он **не делает метрики свежими**: старый сборщик меняет `fetched_at` при ошибке,
включая отсутствие кредитов. Для возраста метрик используются даты фактических
наблюдений. Старые значения без доказанной даты остаются `undated`.

## Проверка и выпуск

1. Локальные unit-тесты и тест на мигрированной изолированной PostgreSQL:
   нули/false, старые и чужие привязки, недавняя неудачная попытка, отсутствие
   вывода персональных полей, READ ONLY у каждого SELECT, неизменность анкет.
2. Снять агрегированный baseline с production только чтением. Не коммитить
   производственные выгрузки в Git и не запускать повторный Meta-запрос.
3. PR, зелёный CI, ревью; выпускать только `instagram_discovery_scheduler`
   из CI-образа merged main по durable deployment процедуре. Остальным
   сервисам новая версия для этого этапа не нужна.
4. После выпуска сверить расписание/бюджет и здоровье верификации; дождаться
   очередного **планового** цикла. Не вызывать `scheduled_batch` вручную.
5. По коду следующего отказа определить дальнейшее исправление. Инвентаризация
   не повышает полноту данных сама по себе: очередь, интервалы по полям и
   восстановление недоступных профилей — последующие отдельные изменения.
